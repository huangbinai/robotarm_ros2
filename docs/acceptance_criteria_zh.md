# 验收依据与执行方法

本文件定义工程门槛，配合[阶段表](project_stage_zh.md)和[架构边界](project_architecture_zh.md)使用。数值分为“当前代码/配置已有边界”和“项目建议的任务指标”；建议指标须在试验前固定，不能把它们描述为已达到的性能或设备厂商规格。

## 1. 验收记录要求

每项至少保存：验收编号、代码版本（dirty 工作区附补丁标识）、依赖版本、执行后端、launch/有效参数、模型/标定/权重身份、输入/样本数、命令、退出码、原始输出或日志路径、逐项判定、未覆盖范围、操作者和复核人。物理试验另记设备、负载、初始位置、停止方式和测量数据。

模板见 [TEMPLATE.md](acceptance_records/TEMPLATE.md)。结论统一为 `PASS` / `FAIL` / `NOT_RUN` / `BLOCKED`；跳过不是通过。有安全边界违例、虚报成功、执行器争用或无反馈仍运动的试验不得按总体成功率通过。

## 2. 工程与仿真门槛

| 编号 / 阶段 | 要证明什么 | 通过条件 | 证据或方法 |
| --- | --- | --- | --- |
| ENG-01 / S1 | 包职责和代码依赖可持续维护 | 普通检查退出 0，检查器回归全通过；未增加未批准依赖 | `tools/check_architecture.py` + `tests/test_architecture_guard.py` |
| ENG-02 / S1 | 依赖和资源可独立部署 | 严格检查退出 0；ARCH-01/02/03 关闭；依赖声明和资源路径不靠旧 install 补齐 | 严格报告、迁移 diff、干净构建及相关入口验证 |
| ENG-03 / S1 | 源码可复现构建 | 新构建/安装目录中所有当前包成功；构建/测试失败数 0；列明外部依赖与补丁 | `colcon` 日志、依赖版本和权重校验；新目录构建与全新依赖环境复现分别记录 |
| ENG-04 / S1 | 范围和测试证据准确 | 语音包不再被源码、launch、ROS 包索引发现；核心边界、反馈、轨迹、夹爪、取消/失能都有当前回归证据 | 源码/包清单、回归报告；选择性测试不能替代全部控制器验收 |
| SIM-01 / S2 | 模型可运行且接触数值稳定 | 无头套件各子项 `ok=true`；8 关节/8 执行器，状态有限；接触阈值全部满足 | `mujoco_acceptance --skip-renderer` 的完整 JSON |
| SIM-02 / S2 | ROS 和 MoveIt 真正接通仿真 | ROS 接口验收、MoveIt 规划/执行均成功；轨迹/状态仅来自所选后端；取消/拒绝可观察；无真机节点 | ROS 图、Action 结果、仿真时钟及轨迹日志；GUI 显示另附记录 |
| SIM-03 / S2 | 多后端协议一致且限制差异已处理 | 名称/单位/关节顺序一致；NaN、越界、时间倒序、起点偏差均得到预期结果；取消不被报成功；fake 开度差异 ARCH-04 已解决 | fake/MuJoCo/控制器假硬件的同一组输入和逐项结果 |
| SIM-04 / S2 | Real2Sim 映射正确 | 合成 mirror 检查 200 样本、状态有限、最大关节误差 ≤ `1e-8 rad`；另验证错序/断流拒绝和只读性 | `real2sim_acceptance --mode mirror`；真实状态/physics 模式需另立记录 |

服务和状态所有权的必验项：应用组合中每个命名空间只有一个 teach 录制节点；控制器不注册录制服务；重复 JointState 时间戳不重复写入；Dashboard 不发布 `/joint_states` 或 `/gripper/state`；仿真夹爪无后端不能成功，成功/失败必须来自后端响应。这些已有自动回归，分布式或手工重复启动仍需 ROS 图检查。

SIM-01 现有接触检查门槛来自 `mujoco_acceptance.py`：600 步观测内有效手指接触步数至少 100，接触力不超过 `20 N`，方块单步跳变不超过 `0.005 m`，最低高度不低于 `0.018 m`。这些是该仿真场景的回归阈值，不是机械臂真实接触安全额定值。

现有 Reach/Pick 无头子项是环境冒烟测试，`ok=true` 允许 `is_success=false`。Renderer 的 `renderer_available` 也不参与 health 的总体 `ok` 判定。任务能力、渲染能力必须单独读字段和验收，不能只检查总退出码。

## 3. 真机、操作与示教门槛

以下为待执行的验收方案，本次架构维护不会据此自动启动真机或发运动命令。

| 编号 / 阶段 | 场景 | 通过条件 | 必需证据 |
| --- | --- | --- | --- |
| HW-01 / S3 | 连接不使能、反馈刷新、断流 | 状态区分连接/使能；各电机反馈序号及时间推进；重复/无效帧不刷新新鲜度；超出配置 `0.15 s` 的旧反馈不能获得运动许可 | 逐电机反馈与状态时间序列；50 Hz 是配置目标，还需测量实际分布 |
| HW-02 / S3 | 使能、小幅低速轨迹、到位保持 | 非法轨迹/忙碌/故障不使能；有效轨迹先校验再执行；跟踪/最终误差在有效配置范围内；失败不得返回成功 | 目标与实际轨迹、仲裁状态、Action 状态/错误码、使能前后状态 |
| HW-03 / S3 | 取消、停止、失能、反馈丢失和关闭 | 不产生取消后的新轨迹；验证停止/失能结果；失能失败不报告成功；未知物理状态明确记录；退出行为符合入口配置 | 停止请求到状态变化的时间/位移；新反馈证据；物理急停单独记录 |
| HW-04 / S3 | 夹爪开度、校零、接触与中断 | `0–0.085 m` 内命令符合约定；超限/NaN/Inf 拒绝；校零使用新反馈；空夹闭到底不能冒充抓物；超时/停止正确结束 | 开度/反馈/速度/力矩/结果，空夹与有物两类样本 |
| OPS-01 / S4 | RViz/Web/键盘预览、执行和多入口竞争 | 预览不运动；真机 RViz 合法 Execute 按策略使能；拒绝/取消可显示；默认 reject 仲裁下资源繁忙不产生并发动作 | 端到端操作记录；包含另一个 ROS 客户端，不只检查 UI |
| TEACH-01 / S2/S4 | 录制、文件损坏、轨迹准备与 dry-run | 原始记录经过校验、去重、重采样/重定时、起点及碰撞预检；空文件/无效时间/跳变/越界不进入执行；dry-run 不发执行目标 | 输入 JSONL、prepared trajectory、质量报告、未发送目标的观测证据 |
| TEACH-02 / S4 | 回放、取消、偏差、恢复 | 起点对齐通过后执行；跟踪异常触发预定停止；恢复不能绕过健康/碰撞检查；重复回放结果有统计 | 建议先固定同一轨迹连续 10 次，逐次记录成功/失败原因；与硬件安全项同时满足 |

当前控制器配置的轨迹起点容差为 `0.10 rad`，最终到位容差 `0.03 rad`，settle timeout 为 `2.0 s`；MoveIt 的起点容差另有更严格值。这些数值应随每次参数快照保存，不能替代任务自身所需的位置精度。

物理停止的最大允许时间/位移、负载和工作空间必须由维护者在试验前按现场条件填写。未给出这些判据时，相应物理验收保持 `BLOCKED`，不能仅凭“看上去停了”通过。软件 Stop、失能与物理急停分别验收。

## 4. 视觉门槛

| 编号 / 阶段 | 场景 | 通过条件 | 必需证据 |
| --- | --- | --- | --- |
| VIS-01 / S5 | 相机、内参、手眼、TCP、TF、推理输入 | 彩色/深度/内参时间与设备对应；坐标方向/单位一致；标定残差满足试验前设定阈值；权重校验匹配 | 设备身份、原始标定样本/残差、TF、配置/权重校验、推理样本 |
| VIS-02 / S5 | `plan_only`、候选筛选与无效输入 | 有效候选可形成可达计划；无候选/断流/过期/越界/IK 或碰撞失败时拒绝且不执行旧计划；预览无运动 | 每类失败至少一个固定输入案例、计划/拒绝原因、执行接口观测 |
| VIS-03 / S5 | 真机抓取/抬升/放置和失败恢复 | 试验前固定对象、位置、光照、负载和成功定义；无越界或失控；失败及时终止/恢复且不虚报成功；任务指标达到约定 | 建议首轮 ≥30 次覆盖 ≥3 个固定摆放条件，目标成功率 ≥90%；保留失败样本、耗时与重试次数 |

VIS-03 的次数、覆盖范围和成功率是**建议首版指标，待维护者按任务确定**；没有确定阈值不能宣布阶段通过。成功应包含实际抓住、抬升和放入指定区域，单纯夹爪闭合或 Action 返回不构成任务成功。30 次的局部结果也不代表长期可靠性，长期运行应另定时长/负载与维护要求。

VIS-01/02 的本机 ROS 路线还要求：三个感知节点使用同一可用 Python 环境；真实 SDK depth scale 与 CameraInfo 生效；C2D/去畸变后尺寸及光学坐标一致；四路消息按采集时间精确同步；候选和计划不重置时间；采集时刻 TF 可查询；断流/推理异常产生空结果。合成 ROS 测试与实际相机/模型推理分别记录，见[本机视觉说明](local_ros_vision_zh.md)。

## 5. 可重复的无硬件检查

从仓库根目录执行；前两条只需 Python 标准库：

```bash
python3 tools/check_architecture.py
python3 -m unittest discover -s tests -p 'test_architecture_guard.py' -v
```

已具备本工作区 ROS/venv 安装时：

```bash
source tools/source_ubuntu_env.bash
python -m pytest -q tests
PYTHONPATH="$PWD/src/rebotarm_simulation:$PYTHONPATH" python -m rebotarm_simulation.mujoco_acceptance --skip-renderer
PYTHONPATH="$PWD/src/rebotarm_simulation:$PYTHONPATH" python -m rebotarm_simulation.real2sim_acceptance --mode mirror
```

`source_ubuntu_env.bash` 当前依赖 `/opt/ros/jazzy`、`.venv-ros`、`install-venv`，可选本地 `.ros-overlay`；它不是从零部署脚本。新环境应先完成依赖安装与构建，不能忽略 source 错误后继续计入验收。上述测试使用假硬件或进程内物理仿真，不连接机械臂。

严格门禁单独执行，五项迁移后预期退出 0；它只验证静态依赖与已编码的归属规则：

```bash
python3 tools/check_architecture.py --strict-deployment
```

ROS 集成验收需使用独立的 ROS domain，先检查所选域中没有真机控制器，再启动一个仿真后端。已有工具为 `rebotarm_mujoco_ros_acceptance`、`rebotarm_mujoco_moveit_acceptance`；后者会给当前 Action server 发送轨迹，名称带 “mujoco” 不构成后端隔离保证。当前两项均已有仿真通过记录；`tools/verify_sim_workflows.py` 将标准启动、MoveIt、网页控制、停止、示教预检查和实际回放组合为可重复检查，详见[功能修复复测](acceptance_records/2026-09-11-functional-fixes.md)。
