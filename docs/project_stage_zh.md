## 状态词的统一含义

| 状态 | 可以据此作出的判断 |
| --- | --- |
| 已实现 | 当前源码中存在入口与实现，不代表测试或集成通过 |
| 局部验证 | 已完成列明的自动测试或试验，结论仅覆盖其场景 |
| 阶段通过 | 该阶段全部必需验收项通过，并有版本/配置/日志与复核记录 |
| 待验收 | 缺少当前基线证据，不能推断功能不存在或已稳定 |
| 实验性 | 研究或调试能力，不能作为主链路交付承诺 |
| 暂缓/删除 | 不纳入当前维护和阶段退出条件 |

测试、仿真、真机三个证据维度分别记录。禁止用“全功能完成”“测试全部通过”概括未覆盖的范围。

## 下一批维护工作的顺序

1. **补齐 S1 剩余证据**：架构迁移和新目录构建已完成；接下来补齐控制器反馈、限位、关闭、失能等关键回归，并在全新依赖环境复现部署。
2. **补齐 S2 接口合同**：逐后端测试轨迹拒绝/取消/完成、唯一 server、状态来源、仿真时钟及夹爪范围；补齐长期运行与故障恢复。fake 与真机开度默认值差异由 ARCH-04 跟踪。
3. **建立 S3 实机记录**：先连接不使能与反馈/失能，再小幅运动、停止及异常恢复。固定配置和试验范围，保存原始测量。
4. **在通过的底座上交付 S4/S5**：示教/操作先闭环，视觉从现场标定和 `plan_only` 到低速任务统计；每次只扩大已验证的场景。

具体责任按包归属执行；实际操作者、复核人和执行日期在每份验收记录中填写，不预填不存在的负责人或截止日期。

## 状态如何更新
