# reBotArm MuJoCo STL 凸分解碰撞模型设计

**日期：** 2026-07-12  
**状态：** 已由用户确认，待实施  
**目标：** 将 MuJoCo 中 reBotArm 与夹爪的默认碰撞表示从基础几何体替换为可重复生成的 STL 凸分解模型，为后续精细抓取强化学习提供更贴近机械外形、同时满足 MuJoCo 凸碰撞约束的物理底座。

## 1. 背景与边界

MuJoCo 可以加载 STL mesh，但原始 mesh 用于碰撞时实际采用整体凸包。直接引用一个包含凹槽、夹爪内侧或复杂外形的原始 STL，会把凹陷区域填平，不能等同于逐三角面精确碰撞。

本设计采用 VHACD 将每个原始视觉 STL 分解为多个凸 STL。每个凸块分别作为 MuJoCo mesh geom，从而以有限数量的凸体组合近似原始凹形轮廓。

本阶段只更换碰撞表示和相关验证：

- 不实现强化学习算法、Gymnasium 环境、奖励函数或训练任务；
- 不改变 ROS 2、MoveIt、轨迹、夹爪和 Python 仿真 API 的外部语义；
- 不连接、启用或驱动真实机械臂；
- 不把基础 box、cylinder 等碰撞体保留为默认或静默回退方案。

## 2. 模型结构

原始 STL 继续只负责视觉显示。凸分解结果放入独立目录：

```text
src/rebotarm_simulation/models/rebotarm/
├── assets/                         # 原始视觉 STL
├── collision_vhacd/                # 版本控制下的凸分解 STL
│   ├── base_link/
│   │   ├── hull_000.stl
│   │   └── ...
│   ├── link1/
│   ├── ...
│   ├── gripper_base/
│   ├── left_finger/
│   └── right_finger/
├── collision_vhacd_manifest.json   # 输入哈希、工具版本、参数和输出清单
├── robot.xml
└── scene.xml
```

`robot.xml` 中：

- `*_visual` geom 继续引用原始 STL，并固定 `contype="0" conaffinity="0"`；
- 每个刚体挂载一组命名为 `*_collision_hull_NNN` 的 mesh geom；
- 凸块 geom 使用统一碰撞类别、摩擦和接触参数；
- 相邻连杆过滤继续通过现有 body-level `contact/exclude` 管理；
- 所有活动刚体继续使用现有显式质量、质心和惯量，凸块不得参与惯量推导。

## 3. 可重复生成流程

仓库提供独立生成脚本，但运行时和普通构建不自动重新分解。脚本职责为：

1. 读取明确列出的 10 个视觉 STL；
2. 计算每个输入文件 SHA-256；
3. 使用固定版本的 VHACD 实现和固定参数分解；
4. 对输出进行稳定排序和连续编号；
5. 写出二进制或 ASCII STL（由工具能力固定一种格式）；
6. 生成 manifest，记录工具版本、参数、输入哈希、每个凸块的哈希、顶点数、面数和包围盒；
7. 在 `--check` 模式下重新计算并确认现有产物与 manifest 一致，不改文件。

生成脚本必须在 Windows 和 Ubuntu 上产生几何等价且清单一致的结果。如果底层 VHACD 输出存在平台浮点差异，则 Windows 仍为受版本控制的产物来源，Ubuntu 通过 manifest 和文件 SHA-256 验证，不在构建时再生成。

## 4. 分解精度策略

采用分部参数而不是所有网格使用同一预算：

- `base_link`、`link1`～`link6`：目标每个部件约 4～12 个凸块；
- `gripper_base`：目标约 8～16 个凸块；
- 左右夹爪：目标各约 8～20 个凸块，优先保持指尖、内侧接触面和开口；
- 超出目标不是立即失败，但必须由接触精度或拓扑需求解释，并受全模型性能门槛约束。

参数调节顺序：先保证夹爪内侧和指尖轮廓，再保证腕部与连杆外轮廓，最后减少不影响接触的细碎凸块。不得仅为通过性能测试而删除精细抓取所需的接触面。

## 5. 验证与验收

### 5.1 静态契约

- 所有视觉 geom 不参与碰撞；
- 所有机器人碰撞 geom 均为 `type="mesh"` 并引用 `collision_vhacd/`；
- 不存在作为机器人默认碰撞体的 box、cylinder、capsule 或原始视觉 STL；
- manifest 覆盖全部输入和输出，文件哈希匹配；
- 每个凸块非空、顶点和面为有限值、可由 MuJoCo 编译；
- 模型质量、惯量、关节方向、零位和限位不因碰撞替换而变化。

### 5.2 物理行为

- 标准零位没有错误的机器人自碰撞；
- 已知折叠合法姿态仍能检测非相邻连杆碰撞；
- 已知合法姿态能检测机械臂与工作台接触；
- 方块能与左右夹爪的凸分解碰撞体分别产生可读接触；
- 默认方块落桌稳定性不退化；
- 多步仿真中位置、速度、执行器力和接触力保持有限，不出现求解器发散。

夹爪接触测试只证明接触可检测，不把第一版凸分解声明为真实材料、柔性指垫或毫米级实机接触复现。

### 5.3 性能

在 Ubuntu VM 的同一 MuJoCo 版本和固定 headless 基准下记录：

- 总凸块数和每个部件凸块数；
- 模型加载时间；
- 固定 10,000 步无渲染仿真耗时和实时系数；
- 接触峰值数量；
- 与替换前基础几何体基线的倍率。

第一版验收门槛：10,000 步 headless 仿真必须完成、无数值错误，且耗时不超过现有基础几何体基线的 5 倍。该门槛防止不可训练的明显退化，不代表未来云端并行强化学习的最终吞吐要求。

### 5.4 双端和集成

- Windows 和 Ubuntu VM 的 MJCF、manifest、生成脚本及全部凸块 STL SHA-256 一致；
- Windows 聚焦测试与 Ubuntu MuJoCo 运行测试通过；
- Ubuntu 三个相关 ROS 2 包构建通过；
- EGL 健康检查、headless CLI 和 Viewer 加载新模型；
- ROS 2 轨迹、夹爪、停止和状态接口保持通过；
- MoveIt 到 MuJoCo 的非硬件轨迹链保持通过；
- 所有启动入口继续默认 `use_hardware:=false`，测试前后无硬件控制进程。

## 6. 失败处理

- 某 STL 无法稳定分解时，生成脚本必须明确失败并指出部件，不得自动退回基础几何体；
- 产物与 manifest 不一致时，检查模式失败，不在运行时自动覆盖；
- 出现零位假碰撞时，先检查凸分解质量和部件坐标，不通过扩大接触排除范围掩盖非相邻碰撞；
- 性能超过 5 倍门槛时，优先合并对接触轮廓贡献小的凸块，夹爪内侧和指尖精度最后降级；
- Ubuntu 平台修复必须同步回 Windows 主副本，再重新执行哈希验证。

## 7. 完成标准

只有以下条件全部成立才算完成：

1. 10 个机器人/夹爪视觉 STL 均有受版本控制的凸分解碰撞产物；
2. MJCF 默认只使用这些凸块作为机器人碰撞体；
3. 生成脚本和 manifest 能重复检查全部资产；
4. 关节、质量、惯量和 ROS 2 外部接口保持不变；
5. 自碰撞、工作台接触、双指方块接触和稳定性测试通过；
6. Ubuntu 加载、EGL、headless、Viewer、构建和 ROS 2/MoveIt 无硬件验证通过；
7. 固定 10,000 步基准不超过基础几何体基线的 5 倍且数值稳定；
8. Windows 与 Ubuntu 本轮全部相关源文件和凸块哈希一致；
9. 全程不连接或驱动实机，仓库中不新增强化学习训练实现。
